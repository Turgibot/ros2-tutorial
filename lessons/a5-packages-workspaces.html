A5 · Packages and workspaces

Create a package of your own, build it in a workspace, and understand how several workspaces stack on top of each other, which is how your code will sit on top of the Kinova software.

1. Goal

In A1 to A4 you used a package.xml and a CMakeLists.txt that were handed to you, and ran colcon build and source without knowing exactly what they do. This lesson explains them. Every program in the course ends up in a package, and the Kinova software is a workspace full of packages, so you need to know how to make one and how it is found.

At the end of this lesson you will have:

  • created a package with ros2 pkg create, read the files it contains, built it and run its program,
  • seen what editing and rebuilding does, and what --symlink-install changes,
  • built a second workspace that overlays the first, and seen in which order ROS 2 searches them,
  • looked at how a package declares its dependencies, using a Kinova package as the example.

2. Concepts

Package

A package is a folder with a package.xml file in it. It is the unit that ROS 2 builds, installs, finds by name (ros2 run a5_hello hello: a5_hello is the package) and shares. A package holds code, and possibly interfaces (.msg, .srv, .action files as in A2 and A3), launch files and parameter files (A4).

  • package.xml says who the package is (name, version, maintainer, license) and what it depends on.
  • A second file says how to build it. The build type picks the tool: ament_cmake (CMakeLists.txt) for C++, interfaces, or a mix of languages, and ament_python (setup.py) for pure Python. A4 used ament_cmake for both languages, because it contained both.

Workspace

A workspace is a folder that holds packages in a src/ folder. colcon build, run in the workspace folder, finds every package under src/, builds them in dependency order, and creates the three folders you know from A0: build/, install/ and log/. In A1 to A4 the workspace and the package were the same folder, to keep things short. From now on we use the normal layout:

my_ws/
  src/
    a5_hello/        the package: package.xml, code, ...
  build/             (created by colcon)
  install/           (created by colcon)
  log/               (created by colcon)

Underlay and overlay

Workspaces can be stacked. ROS 2 itself is a workspace (/opt/ros/jazzy), the Kinova software is another (built on top of it), and yours can be a third. A workspace that you source after another one is an overlay on it, and the first is its underlay. When two workspaces contain a package with the same name, ROS 2 uses the one from the overlay. The order of sourcing decides, as you will see in step 5. This is how you can replace one package of a big system with your own modified copy, without touching the original.

  2. Read the package files

    This is src/a5_hello/package.xml, as generated:

    <?xml version="1.0"?>

  <test_depend>ament_flake8</test_depend>
  <test_depend>ament_pep257</test_depend>

  </export>
</package>
    <?xml version="1.0"?>
<?xml-model href="http://download.ros.org/schema/package_format3.xsd" schematypens="http://www.w3.org/2001/XMLSchema"?>
<package format="3">
  <name>a5_hello</name>
  <version>0.0.0</version>
  <description>My first package</description>
  <maintainer email="ubuntu@todo.todo">ubuntu</maintainer>
  <license>Apache-2.0</license>

  <buildtool_depend>ament_cmake</buildtool_depend>

  <test_depend>ament_lint_auto</test_depend>
  <test_depend>ament_lint_common</test_depend>

  <export>
    <build_type>ament_cmake</build_type>
  </export>
</package>
    • name, version, description, maintainer, license: the identity. The name must be unique among the packages you have, and is what you type after ros2 run. The author and license are placeholders you would change for a package you share.
    • export / build_type: which build tool builds it.
    • The depend lines say what the package needs. They are explained in step 6. This package needs nothing but its build tool, so there are none yet apart from the tests.

    The build file for ament_python is setup.py:

    from setuptools import find_packages, setup

package_name = 'a5_hello'

setup(
    name=package_name,
    version='0.0.0',
    packages=find_packages(exclude=['test']),
    data_files=[
        ('share/ament_index/resource_index/packages',
            ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
    ],
    install_requires=['setuptools'],
    zip_safe=True,
    maintainer='ubuntu',
    maintainer_email='ubuntu@todo.todo',
    description='My first package',
    license='Apache-2.0',
    extras_require={
        'test': [
            'pytest',
        ],
    },
    entry_points={
        'console_scripts': [
            'hello = a5_hello.hello:main'
        ],
    },
)
    • packages=find_packages(...): the Python code to install (the folder a5_hello/ with __init__.py and hello.py).
    • data_files: extra files to copy into install/a5_hello/share/a5_hello: the package.xml, and the empty file resource/a5_hello, whose only job is to register the package name with ROS 2.
    • entry_points / console_scripts: 'hello = a5_hello.hello:main' means "make a program called hello that runs the function main of the module a5_hello.hello". That is what ros2 run a5_hello hello starts. The file setup.cfg tells the build to put that program in lib/a5_hello, where ros2 run looks.

    And the program itself, a5_hello/hello.py, is two lines of Python: main() prints Hi from a5_hello.

    The build file for ament_cmake is CMakeLists.txt. The generated one also has comments and a block for tests, left out here. The compiler options and target_* lines in the middle are boilerplate you can ignore:

    cmake_minimum_required(VERSION 3.8)
project(a5_hello)

if(CMAKE_COMPILER_IS_GNUCXX OR CMAKE_CXX_COMPILER_ID MATCHES "Clang")
  add_compile_options(-Wall -Wextra -Wpedantic)
endif()

find_package(ament_cmake REQUIRED)

add_executable(hello src/hello.cpp)
target_include_directories(hello PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<INSTALL_INTERFACE:include/${PROJECT_NAME}>)
target_compile_features(hello PUBLIC c_std_99 cxx_std_17)  # Require C99 and C++17

install(TARGETS hello
  DESTINATION lib/${PROJECT_NAME})

ament_package()
    • project(a5_hello): the package name again. It must match package.xml.
    • find_package(ament_cmake REQUIRED): the build tool. Each package you depend on also needs a find_package line here (as in A1: rclcpp, std_msgs).
    • add_executable(hello src/hello.cpp) (followed by the target_include_directories and target_compile_features boilerplate): compile this file into a program called hello.
    • install(TARGETS hello DESTINATION lib/${PROJECT_NAME}): put it in install/a5_hello/lib/a5_hello, where ros2 run looks. Without an install line, the program is built but never found.
    • ament_package() must be the last line.

    And the program itself, src/hello.cpp, is a main that prints hello world a5_hello package with printf. It does not use ROS 2 at all: a package does not have to.

  4. Edit, rebuild, and --symlink-install

    Change the message the program prints (the command below does it for you; you can also edit the file by hand), then run the program without building:

    sed -i 's/Hi from a5_hello\./Hi from a5_hello, version 1./' src/a5_hello/a5_hello/hello.py
ros2 run a5_hello hello
    sed -i 's/hello world a5_hello package/hello from a5_hello, version 1/' src/a5_hello/src/hello.cpp
ros2 run a5_hello hello
    Hi from a5_hello.
    hello world a5_hello package

    Still the old message: ros2 run runs what is in install/, and install/ holds a copy made at the last build, not your source file. Build again:

    colcon build
ros2 run a5_hello hello
    Starting >>> a5_hello
Finished <<< a5_hello [0.47s]

Summary: 1 package finished [0.52s]
Hi from a5_hello, version 1.
    Starting >>> a5_hello
Finished <<< a5_hello [0.10s]

Summary: 1 package finished [0.14s]
hello from a5_hello, version 1

    Having to rebuild after every edit gets tedious. The option --symlink-install makes install/ hold links to your source files instead of copies, for the files that are simply copied:

    colcon build --symlink-install
source install/setup.bash
sed -i 's/version 1/version 1b/' src/a5_hello/a5_hello/hello.py
ros2 run a5_hello hello
    Starting >>> a5_hello
Finished <<< a5_hello [0.63s]

Summary: 1 package finished [0.67s]
Hi from a5_hello, version 1b.

    The edit took effect without a build. Source the workspace again after switching to --symlink-install: the way Python finds the package changes, and the old shell would fail with No package metadata was found for a5-hello. So with Python, every code edit is live. Put the message back with sed -i 's/version 1b/version 1/' src/a5_hello/a5_hello/hello.py.

    colcon build --symlink-install
source install/setup.bash
sed -i 's/version 1/version 1b/' src/a5_hello/src/hello.cpp
ros2 run a5_hello hello
    Starting >>> a5_hello
Finished <<< a5_hello [0.30s]

Summary: 1 package finished [0.35s]
hello from a5_hello, version 1

    Still version 1: a compiled program must be compiled again, links or not. What --symlink-install helps with in C++ packages is the files that are only copied: launch files, YAML files and Python scripts (the exercise below uses this). Put the message back with sed -i 's/version 1b/version 1/' src/a5_hello/src/hello.cpp and run colcon build.

  5. Stack a second workspace on the first

    Which workspaces does this shell search, and in what order? ROS 2 keeps the list in AMENT_PREFIX_PATH. Print its first three entries:

    echo $AMENT_PREFIX_PATH | tr : '\n' | sed -n '1,3p'
    /workspace/code/05-packages/my_ws/install/a5_hello
/opt/kortex_ws/install/kortex_bringup
/opt/kortex_ws/install/kinova_gen3_lite_moveit_config

    Your workspace is first, then the Kinova packages (the list continues with the rest of the Kinova workspace and, at the very end, /opt/ros/jazzy). The list is searched from the top. Sourcing a workspace adds its packages to the front.     Why this matters for the arm The Kinova software is an overlay on ROS 2, and the Docker run script sources it for you. Your own packages in later lessons will be one more overlay on top of it, built in a shell where both are sourced.

  6. Declare what a package needs

    A package lists the other packages it needs in package.xml. Look at the list of a Kinova package. ros2 pkg prefix --share gives the folder where the installed package.xml sits:

    grep depend $(ros2 pkg prefix --share kortex_bringup)/package.xml | head -8
      <buildtool_depend>ament_cmake</buildtool_depend>
  <buildtool_depend>ament_cmake_python</buildtool_depend>
  <exec_depend>rclpy</exec_depend>
  <exec_depend>controller_manager</exec_depend>
  <exec_depend>joint_state_publisher</exec_depend>
  <exec_depend>launch</exec_depend>
  <exec_depend>launch_ros</exec_depend>
  <exec_depend>rviz2</exec_depend>

    There are a few kinds of dependency:

    TagMeaningExample
    buildtool_dependa tool needed to build the packageament_cmake
    build_dependneeded to compile (headers, libraries)std_msgs in a C++ package
    exec_dependneeded only to runrclpy, rviz2 above
    dependboth of the previous (the usual choice)rclcpp (our A1 package used this)
    test_dependneeded only for testsament_lint_auto

    The list is used twice. colcon build builds packages in the order their dependencies need. And rosdep install --from-paths src reads it to install the system packages that are missing: this is what the Dockerfile (and the local install in A0) did to install Gazebo, MoveIt 2 and ros2_control for the Kinova workspace. For a C++ package, a dependency also needs a find_package(...) line in CMakeLists.txt, as you did in A1.

4. Check

You are done when:

  • ros2 run a5_hello hello prints your message from my_ws, and ros2 pkg prefix a5_hello points into my_ws/install,
  • in a shell where only my_ws2 is sourced it prints version 2, and the first entry of AMENT_PREFIX_PATH is in my_ws2,
  • ros2 pkg prefix --share kortex_bringup prints a folder under /opt/kortex_ws/install (under ~/kortex_ws/install in a local install).
Done when all three are true.

5. Exercise

In A4, changing config/announcers.yaml had no effect until you ran colcon build again. Rebuild code/04-parameters-launch so that you never need to rebuild after editing that file (in a fresh shell, in that folder), then change name: putdown to name: pickup in the YAML file and launch. What do you build with, and what do you hear?

Answer 
cd code/04-parameters-launch
colcon build --symlink-install
source install/setup.bash

Now install/a4_params/share/a4_params/config is a link to your source folder, so ros2 launch a4_params announcers.launch.py reads your edited file at once. After the edit the listener hears pickup F (planner_b) in place of putdown F, with no rebuild. We ran exactly this (with the Python programs). The edit of a launch file works the same way.

6. Recap

  • A package is a folder with a package.xml, plus a build file: CMakeLists.txt (ament_cmake, for C++ and interfaces) or setup.py (ament_python). ros2 pkg create --build-type ... --node-name ... name makes a working one.
  • A workspace holds packages in src/; colcon build in its folder creates build/, install/ and log/. colcon list shows what it found.
  • ros2 run runs what is in install/, a copy made at build time. Rebuild after edits, or use colcon build --symlink-install (and source again) for Python, launch and YAML files. Compiled C++ always needs a build.
  • Overlay: a workspace sourced after another one wins for packages with the same name, and remembers its underlays. AMENT_PREFIX_PATH is the search list, front first.
  • package.xml declares dependencies (depend, exec_depend, ...). colcon uses them for build order and rosdep install for system packages.
