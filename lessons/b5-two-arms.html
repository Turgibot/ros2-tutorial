B5 · Two arms in one scene

Two Gen3 arms, one robot description, one MoveIt. Each arm plans on its own, and MoveIt knows that the other arm is an obstacle.

1. Goal

The course ends with two arms working in the same space (parts D and E). In B4 you used one arm and one set of names: joint_1, base_link, the group manipulator. Two arms cannot share those names. This lesson shows what has to change, and it is less than you may expect: a prefix in front of every name, and a few files that list those names.

At the end of this lesson you will have:

  • built a robot description with two arms (left_ and right_) standing 1 m apart and facing each other,
  • started MoveIt with two planning groups, left_arm and right_arm, and one controller for each arm,
  • moved each arm from a program, with poses in one shared frame, world,
  • seen MoveIt refuse a goal for one arm because the hand of the other arm is already there,
  • and seen what START_STATE_INVALID means, and how to recover from it.
Read this first: what is different here

The Kinova packages ship a file for two arms (kortex_dual_robots.xacro), but it does not work: it passes an argument (sim) that the arm macro no longer has, and xacro stops with Invalid parameter "sim". There is also no MoveIt configuration for two arms. So the files of this lesson are written by this course, from the single-arm files, and they are not tested with a real pair of arms. The arms here have no gripper (to keep the lesson short), and they run on fake hardware.

2. Concepts

Names must be unique

ROS 2 identifies a joint, a link or a frame by its name. Two arms that both have joint_1 would be one joint twice, which is an error. The arm macro of the Kinova description takes a prefix and puts it in front of every link, joint and hardware name. With prefix="left_" the first joint is left_joint_1, the base is left_base_link, the hand is left_end_effector_link. A second copy with prefix="right_" gives the right arm. Both hang from the same fixed link, world, at different places.

Which files hold names

Everything that mentions a joint or link by name must be told about both arms. For MoveIt and ros2_control that is a handful of files:

File (in code/b5-dual/config)What it saysWhat changed from one arm
dual.urdf.xacrothe robot: links, joints, and one ros2_control block per armthe arm macro used twice, with a prefix and a base position (this one is new)
ros2_controllers.yamlthe controllers of ros2_control and their jointsone joint_trajectory_controller per arm, with prefixed joint names
dual.srdfplanning groups, and which link pairs never collidetwo groups (left_arm, right_arm); the "never collide" pairs once per arm
kinematics.yamlthe IK solver of each groupone entry per group
joint_limits.yamlspeed and acceleration limits per jointevery joint name prefixed
ompl_planning.yamlthe planner settings per groupone section per group
moveit_controllers.yamlwhich controller executes a MoveIt trajectoryone entry per arm

Only the first file is written by hand. The others come from the files that ship for one arm, by a short script (scripts/make_config.py, already run): it copies each file and puts the prefix in. You do not need to run it, but its source is below, so you can see exactly what "adding a prefix" means for each file.

One controller manager, or two?

There are two ways to run two arms. You can start one controller_manager that controls both arms (each arm has its own joint_trajectory_controller), or two, each in its own ROS namespace, as you would for two real robots with their own driver. This lesson uses one: it needs no namespaces, and everything stays visible in the same lists you know from A7. For two real arms, the ros2_control block of each arm has its own robot_ip in the description, so the same structure carries over. That is not tested here.

The shared planning scene

In B4 the planning scene held the robot and the boxes you added. Now the robot is both arms, so MoveIt checks every path of one arm against the other arm as well, wherever that arm happens to be. Nothing has to be configured for that: it comes from having both arms in one robot description. The group right_arm only decides which joints MoveIt moves; the left arm is still in the scene as an obstacle, standing at its current joint values.

One world frame

In B4 poses were given in base_link. With two bases, a pose "in the base frame" is ambiguous. The programs of this lesson take poses in world, the frame both bases are fixed to, so the same numbers mean the same place for both arms.

    How the files were made: scripts/make_config.py

    This is the script that produced six of the seven files from the single-arm ones. It is a good place to see what each file needs. (Run inside a container, because it reads /opt/kortex_ws.) One value is changed on purpose: the IK solver timeout (kinematics_solver_timeout) is 0.05 s instead of 0.005 s of the single-arm file; I raised it hoping for fewer odd solutions and I cannot tell from my runs that it made a difference.

    #!/usr/bin/env python3
"""Build the two-arm MoveIt config files from the single-arm ones that ship with the Kinova packages.

Run it once (it is already run, the results are in config/):
    python3 scripts/make_config.py
It reads /opt/kortex_ws/.../kinova_gen3_7dof_robotiq_2f_85_moveit_config/config and writes into ../config.
The idea of the whole lesson: every joint and link name gets a prefix, "left_" or "right_".
"""
import os
import re

SRC = ("/opt/kortex_ws/install/kinova_gen3_7dof_robotiq_2f_85_moveit_config/share/"
       "kinova_gen3_7dof_robotiq_2f_85_moveit_config/config")
DST = os.path.join(os.path.dirname(os.path.abspath(__file__)), "..", "config")
SIDES = ("left", "right")
JOINTS = [f"joint_{i}" for i in range(1, 8)]


def read(name):
    with open(os.path.join(SRC, name)) as f:
        return f.read()


def write(name, text):
    with open(os.path.join(DST, name), "w") as f:
        f.write(text)
    print("wrote config/" + name)


# 1. SRDF: two groups, and the "never collide" pairs of the single arm, once per arm (no gripper in this lesson)
pairs = [l for l in read("gen3.srdf").splitlines()
         if "<disable_collisions" in l and "robotiq" not in l]
out = ['<?xml version="1.0"?>', '<robot name="dual">']
for s in SIDES:
    out.append(f'  <group name="{s}_arm">')
    out.append(f'    <chain base_link="{s}_base_link" tip_link="{s}_end_effector_link"/>')
    out.append('  </group>')
for s in SIDES:
    out.append(f'  <group_state name="Vertical" group="{s}_arm">')
    out += [f'    <joint name="{s}_{j}" value="0"/>' for j in JOINTS]
    out.append('  </group_state>')
for s in SIDES:
    for l in pairs:
        out.append(re.sub(r'link([12])="(\w+)"', lambda m: f'link{m.group(1)}="{s}_{m.group(2)}"', l.rstrip()))
out.append('</robot>')
write("dual.srdf", "\n".join(out) + "\n")

# 2. kinematics: one KDL solver per group
write("kinematics.yaml", "".join(
    f"{s}_arm:\n  kinematics_solver: kdl_kinematics_plugin/KDLKinematicsPlugin\n"
    "  kinematics_solver_search_resolution: 0.005\n  kinematics_solver_timeout: 0.05\n" for s in SIDES))

# 3. joint limits: the single-arm values, with the prefix on every joint name
lim = read("joint_limits.yaml").split("joint_limits:\n")
head = lim[0]
body = []
for s in SIDES:
    for j in JOINTS:
        m = re.search(rf"  {j}:\n((?:    .*\n)+)", lim[1])
        body.append(f"  {s}_{j}:\n{m.group(1)}")
write("joint_limits.yaml", head + "joint_limits:\n" + "".join(body))

# 4. OMPL: the group sections are renamed, the gripper section is dropped
ompl = read("ompl_planning.yaml")
i = ompl.index("\nmanipulator:")
j = ompl.index("\ngripper:")
section = ompl[i:j].strip("\n").replace("manipulator:", "{g}:", 1)
write("ompl_planning.yaml", ompl[:i].rstrip("\n") + "\n\n" +
      "\n\n".join(section.format(g=f"{s}_arm") for s in SIDES) + "\n")

# 5. MoveIt -> controller: one FollowJointTrajectory controller per arm
ctl = "moveit_controller_manager: moveit_simple_controller_manager/MoveItSimpleControllerManager\n\n"
ctl += "moveit_simple_controller_manager:\n  controller_names:\n"
ctl += "".join(f"    - {s}_joint_trajectory_controller\n" for s in SIDES)
for s in SIDES:
    ctl += f"\n  {s}_joint_trajectory_controller:\n    type: FollowJointTrajectory\n    joints:\n"
    ctl += "".join(f"      - {s}_{j}\n" for j in JOINTS)
    ctl += "    action_ns: follow_joint_trajectory\n    default: true\n"
write("moveit_controllers.yaml", ctl)

# 6. ros2_control: one controller manager, a joint trajectory controller per arm
rc = "controller_manager:\n  ros__parameters:\n    update_rate: 1000  # Hz\n\n"
rc += "    joint_state_broadcaster:\n      type: joint_state_broadcaster/JointStateBroadcaster\n"
for s in SIDES:
    rc += f"\n    {s}_joint_trajectory_controller:\n      type: joint_trajectory_controller/JointTrajectoryController\n"
for s in SIDES:
    rc += f"\n{s}_joint_trajectory_controller:\n  ros__parameters:\n    joints:\n"
    rc += "".join(f"      - {s}_{j}\n" for j in JOINTS)
    rc += ("    command_interfaces:\n      - position\n    state_interfaces:\n      - position\n      - velocity\n"
           "    state_publish_rate: 100.0\n    action_monitor_rate: 20.0\n    allow_partial_joints_goal: false\n"
           "    constraints:\n      stopped_velocity_tolerance: 0.0\n      goal_time: 0.0\n")
write("ros2_controllers.yaml", rc)

# 7. RViz: the single-arm MoveIt layout works as it is (Fixed Frame is "world")
write("moveit.rviz", read("moveit.rviz"))

  5. Move each arm, in the shared frame

    move_arm is the move_pose of B4 with two changes: the first argument says which arm (left or right), and the pose is in world. The program builds the group name (left_arm) and the hand link (left_end_effector_link) from that word.

    #!/usr/bin/env python3
"""Ask MoveIt to move one arm's hand to a pose: move_arm left|right X Y Z ROLL PITCH YAW  (metres, degrees).

The pose is in the frame "world", shared by both arms."""
import math
import sys

import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from geometry_msgs.msg import Pose
from moveit_msgs.action import MoveGroup
from moveit_msgs.msg import (BoundingVolume, Constraints, MoveItErrorCodes,
                             OrientationConstraint, PositionConstraint)
from shape_msgs.msg import SolidPrimitive

WORLD = "world"


def quaternion_from_rpy(roll, pitch, yaw):
    cr, sr = math.cos(roll / 2), math.sin(roll / 2)
    cp, sp = math.cos(pitch / 2), math.sin(pitch / 2)
    cy, sy = math.cos(yaw / 2), math.sin(yaw / 2)
    return (sr * cp * cy - cr * sp * sy,   # x
            cr * sp * cy + sr * cp * sy,   # y
            cr * cp * sy - sr * sp * cy,   # z
            cr * cp * cy + sr * sp * sy)   # w


def error_name(code):
    for name in dir(MoveItErrorCodes):
        if name.isupper() and getattr(MoveItErrorCodes, name) == code:
            return name
    return str(code)


def main():
    if len(sys.argv) != 8 or sys.argv[1] not in ("left", "right"):
        sys.exit("usage: move_arm left|right X Y Z ROLL PITCH YAW   (metres, degrees, frame world)")
    side = sys.argv[1]
    group, tip = f"{side}_arm", f"{side}_end_effector_link"   # names from the SRDF and the URDF
    x, y, z = map(float, sys.argv[2:5])
    roll, pitch, yaw = (math.radians(float(a)) for a in sys.argv[5:8])

    rclpy.init()
    node = Node("move_arm")
    client = ActionClient(node, MoveGroup, "move_action")
    if not client.wait_for_server(timeout_sec=10.0):
        sys.exit("no /move_action: is move_group running?")

    target = Pose()
    target.position.x, target.position.y, target.position.z = x, y, z
    qx, qy, qz, qw = quaternion_from_rpy(roll, pitch, yaw)
    target.orientation.x, target.orientation.y = qx, qy
    target.orientation.z, target.orientation.w = qz, qw

    # position: the hand origin must lie inside a 1 mm sphere around the target
    sphere = SolidPrimitive(type=SolidPrimitive.SPHERE, dimensions=[0.001])
    position = PositionConstraint()
    position.header.frame_id = WORLD
    position.link_name = tip
    position.constraint_region = BoundingVolume(primitives=[sphere], primitive_poses=[target])
    position.weight = 1.0
    # orientation: each axis within 0.01 rad of the target
    orientation = OrientationConstraint()
    orientation.header.frame_id = WORLD
    orientation.link_name = tip
    orientation.orientation = target.orientation
    orientation.absolute_x_axis_tolerance = 0.01
    orientation.absolute_y_axis_tolerance = 0.01
    orientation.absolute_z_axis_tolerance = 0.01
    orientation.weight = 1.0

    goal = MoveGroup.Goal()
    goal.request.group_name = group
    goal.request.num_planning_attempts = 5
    goal.request.allowed_planning_time = 5.0
    goal.request.max_velocity_scaling_factor = 0.3
    goal.request.max_acceleration_scaling_factor = 0.3
    goal.request.goal_constraints = [Constraints(position_constraints=[position],
                                                 orientation_constraints=[orientation])]
    goal.planning_options.plan_only = False   # plan AND execute

    send = client.send_goal_async(goal)
    rclpy.spin_until_future_complete(node, send)
    handle = send.result()
    if not handle.accepted:
        sys.exit("goal rejected")
    done = handle.get_result_async()
    rclpy.spin_until_future_complete(node, done)
    result = done.result().result
    print(f"result: {error_name(result.error_code.val)}")
    points = result.planned_trajectory.joint_trajectory.points
    if points:
        last = points[-1]
        print(f"trajectory: {len(points)} points, {last.time_from_start.sec + last.time_from_start.nanosec * 1e-9:.2f} s")
    node.destroy_node()
    rclpy.shutdown()
    sys.exit(0 if result.error_code.val == MoveItErrorCodes.SUCCESS else 1)


if __name__ == "__main__":
    main()
    // Ask MoveIt to move one arm's hand to a pose: move_arm left|right X Y Z ROLL PITCH YAW  (metres, degrees)
// The pose is in the frame "world", shared by both arms.
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <cstring>
#include <string>
#include <memory>
#include <thread>

#include <geometry_msgs/msg/pose.hpp>
#include <moveit/move_group_interface/move_group_interface.hpp>
#include <rclcpp/rclcpp.hpp>
#include <tf2/LinearMath/Quaternion.h>

int main(int argc, char** argv)
{
  rclcpp::init(argc, argv);
  if (argc != 8 || (std::strcmp(argv[1], "left") != 0 && std::strcmp(argv[1], "right") != 0)) {
    std::fprintf(stderr, "usage: move_arm left|right X Y Z ROLL PITCH YAW   (metres, degrees, frame world)\n");
    return 2;
  }
  const std::string side = argv[1];
  const std::string group_name = side + "_arm";            // names from the SRDF and the URDF
  const std::string tip = side + "_end_effector_link";
  const double x = std::atof(argv[2]), y = std::atof(argv[3]), z = std::atof(argv[4]);
  const double deg = M_PI / 180.0;
  tf2::Quaternion q;
  q.setRPY(std::atof(argv[5]) * deg, std::atof(argv[6]) * deg, std::atof(argv[7]) * deg);

  auto node = std::make_shared<rclcpp::Node>("move_arm");
  // MoveGroupInterface needs the node to be spinning, so spin it in a thread
  rclcpp::executors::SingleThreadedExecutor executor;
  executor.add_node(node);
  std::thread spinner([&executor]() { executor.spin(); });

  moveit::planning_interface::MoveGroupInterface group(node, group_name);
  group.setEndEffectorLink(tip);
  group.setPoseReferenceFrame("world");
  group.setNumPlanningAttempts(5);
  group.setPlanningTime(5.0);
  group.setMaxVelocityScalingFactor(0.3);
  group.setMaxAccelerationScalingFactor(0.3);

  geometry_msgs::msg::Pose target;
  target.position.x = x;
  target.position.y = y;
  target.position.z = z;
  target.orientation.x = q.x();
  target.orientation.y = q.y();
  target.orientation.z = q.z();
  target.orientation.w = q.w();
  group.setPoseTarget(target);

  moveit::planning_interface::MoveGroupInterface::Plan plan;
  const auto planned = group.plan(plan);
  int status = 1;
  if (planned == moveit::core::MoveItErrorCode::SUCCESS) {
    const auto& pts = plan.trajectory.joint_trajectory.points;
    const auto& last = pts.back().time_from_start;
    const auto executed = group.execute(plan);
    std::printf("result: %s\n", executed == moveit::core::MoveItErrorCode::SUCCESS ? "SUCCESS" : "EXECUTION FAILED");
    std::printf("trajectory: %zu points, %.2f s\n", pts.size(), last.sec + last.nanosec * 1e-9);
    status = executed == moveit::core::MoveItErrorCode::SUCCESS ? 0 : 1;
  } else {
    std::printf("result: PLANNING FAILED (error code %d)\n", planned.val);
  }
  executor.cancel();
  spinner.join();
  rclcpp::shutdown();
  return status;
}

The right arm is turned by 180°, so its hand has the "same" pose with the yaw turned by 180° and the x position mirrored. Lm is a pose for the left hand and Rm its mirror image for the right hand: the two hands end up about 10 cm apart in the middle.   6. The other arm is in the way

    Now the test of the shared scene. First take the right arm away to a pose far from the middle, then put the left hand into the middle, and then ask the right arm for the pose it had before:

    result: SUCCESS

    In C++ the last result reads PLANNING FAILED (error code 99999), after an [ERROR] ... MoveGroupInterface::plan() failed or timeout reached line, as in the exercise of B4.

    The first two moves work. The third is the same request that worked a minute ago, and now it fails after about five seconds. Nothing in the request changed: the left hand is now in the middle, about 10 cm from the place where the right hand should go. MoveIt checks the goal pose against the whole robot, and the left arm is part of it, so the goal is in collision. As in B4, the reason is in T2, the terminal of move_group: Unable to sample any valid states for goal tree.

    The same goal works whenever the left arm is not in the way (that was step 5), so this is the other arm and not an unreachable pose. Nothing was added to the scene by hand: the arm was in the scene from the start.

  7. When it says START_STATE_INVALID

    With the planner you will sometimes meet this, in these or other moves:

    result: START_STATE_INVALID

    It means MoveIt refuses to plan from where the arm is now, and it will keep refusing every request for that arm until you fix the state. In T2 it says:

    [ERROR] [move_group]: PlanningRequestAdapter 'CheckStartStateBounds' failed, because 'Start state out of bounds.'. Aborting planning pipeline.

    What I found: some joints (1, 3, 5 and 7) are continuous, they can turn without end (B1). MoveIt's random search sometimes ends a path with such a joint turned past half a turn: for example right_joint_5 at 3.35 rad, when half a turn is π = 3.14 rad. The fake arm accepts that, MoveIt then calls the state "out of bounds". The pose of the hand is fine: 3.35 rad is the same angle as 3.35 − 2π = −2.93 rad. I did not find a setting that prevents it. In my runs it happened from time to time, and more often after long paths (80 or more points for a short move), but long paths alone did not always cause it.

    To recover, put the joint back inside ±π with a trajectory sent straight to the controller (A7), in the equivalent angle. First read the joints, with T3:

    ros2 topic echo /joint_states --once --field position

    Find the joint that is beyond ±π (the order is the order of the names above: left arm first). Then send the whole arm to the same pose with that one joint moved by 2π, for example for right_joint_5 at 3.35 and all the other joints at 0:

    ros2 action send_goal /right_joint_trajectory_controller/follow_joint_trajectory control_msgs/action/FollowJointTrajectory "{trajectory: {joint_names: [right_joint_1, right_joint_2, right_joint_3, right_joint_4, right_joint_5, right_joint_6, right_joint_7], points: [{positions: [0, 0, 0, 0, -2.9332, 0, 0], time_from_start: {sec: 3}}]}}"

    Replace the seven numbers by the values you read, with the joint beyond π replaced by its value minus 2π (or plus 2π if it is below −π). I tried this on the fake arm with a test state: right_joint_5 at 3.35 gave START_STATE_INVALID for every plan; at 3.14 planning worked; and after sending −2.9332 (the equivalent angle) planning worked again. The same joints exist in a single arm, so it may occur there too (I did not see it in B4). If nothing else helps, stop the launch in T2 and start it again: the arms return to their zero pose.

    Two other results you may meet, because the planner is random: INVALID_MOTION_PLAN (a plan was found, but it failed the final check, and the arm did not move) and a plain FAILURE for a pose that is reachable. In both cases ask again.

  • T2 printed You can start planning now!, three controllers are active, and /joint_states lists fourteen joints with the prefixes.
  • The right arm reached Rm, and tf2_echo world right_end_effector_link agrees.

6. Recap

  • Two arms in one robot: use the arm macro twice with a prefix (left_, right_) and a base position. Every joint, link and hardware name gets the prefix.
  • Files that list names need both arms: the ros2_control controllers, the SRDF (two planning groups), the kinematics, joint limits, OMPL and MoveIt controller files. Here a script made them from the single-arm files.
  • One controller_manager with a trajectory controller per arm, one /joint_states with all 14 joints, poses in the shared frame world.
  • The shared scene comes for free: each arm is an obstacle for the other, at its current joint values. A goal that touches the other arm fails.
  • START_STATE_INVALID with "Start state out of bounds" can come from a continuous joint turned past ±π; send the same pose with that joint's equivalent angle (± 2π) straight to the controller.
  • Not tested: a real pair of arms (two robot_ips), the grippers, planning both arms in one request, and namespaces with two controller managers.
