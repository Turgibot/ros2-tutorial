A3 · Actions

Give a robot a job that takes time: watch its progress while it works, get a result at the end, and cancel it on the way.

1. Goal

In A2 we met the symbolic action unstack F W. A real arm needs several seconds to carry it out: move above the block, close the gripper, lift, and so on. A service is the wrong tool for that (the client would wait with no news until the end, and could not stop it), and so is a topic (there is no "this is the answer to my request").

At the end of this lesson you will have:

  • defined an action, Execute, with a goal, feedback and a result,
  • run an action server that pretends to carry out a symbolic action in four phases, and sent it goals from the command line and from a client program,
  • watched the feedback arrive while the goal runs, and cancelled a goal before it finished.

The server here only waits one second per phase. In Part D the same interface will drive a real pick-and-place.

2. Concepts

Goal, feedback, result, cancel

An action is for a job that takes time. It has these parts:

  • the goal: what to do (the client sends it, the server accepts or rejects it),
  • feedback: progress messages, sent by the server while it works,
  • the result: one final message when the job ends,
  • cancel: the client may ask the server to stop early.

It is defined in an action file (.action), which is three message definitions in one file, separated by ---: goal, result, feedback, in that order. It is an interface, like the .msg and .srv files of A2.

A goal always ends in one of three statuses: SUCCEEDED, CANCELED (the client asked to stop and the server did), or ABORTED (the server gave up, for example because the arm hit a limit).

Actions are built from topics and services

Nothing new is needed underneath: an action is a bundle of the two things you already know, used in the way that suits each part.

How. You never create these yourself. When a server offers an action called execute, the ROS 2 library creates three services and two topics under the name /execute/_action/.... When a client connects to execute, it finds them by that name. Their message types are generated from the .action file when you build it. They are hidden from the normal ros2 service list and ros2 topic list, and you will list them below.

PartUsed asHidden nameWhy
Goalservicesend_goalThe client needs an answer: accepted or rejected. A service gives exactly that reply to exactly that caller.
Resultserviceget_resultThe client asks for it when it wants it, and the server answers once the goal has ended. A result published on a topic could be missed if the client was not listening at that moment.
Cancelservicecancel_goalThe client needs to know which goals are now being cancelled (you will see this in the reply).
FeedbacktopicfeedbackA stream of updates, sent whenever the server likes, without waiting for anyone. If one is missed, the next one replaces it.
StatustopicstatusThe state of every goal (accepted, executing, cancelling, ...), sent as it changes, for anyone who wants to watch.

The rule of thumb is the one from A2: a topic for a stream that nobody has to answer, a service for a question that needs an answer. The service and topic messages carry a goal ID (the "Goal accepted with ID: ..." you will see below), so that when several clients send goals at once, each one receives only the feedback and result of its own goal.

  3. Read the server

    This is code/03-actions/py/server.py:

    #!/usr/bin/env python3
"""Action server /execute: pretends to carry out a symbolic action in four phases (1 s each)."""
import time

import rclpy
from rclpy.action import ActionServer, CancelResponse
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor
from rclpy.node import Node
from a3_interfaces.action import Execute

PHASES = ['approach', 'grasp', 'lift', 'place']


class Robot(Node):
    def __init__(self):
        super().__init__('robot')
        # Reentrant group + multi-threaded executor: a cancel request must be handled
        # while execute() is still running.
        ActionServer(self, Execute, 'execute',
                     execute_callback=self.execute,
                     cancel_callback=lambda goal_handle: CancelResponse.ACCEPT,
                     callback_group=ReentrantCallbackGroup())

    def execute(self, goal_handle):
        action = f'{goal_handle.request.name} {" ".join(goal_handle.request.args)}'
        self.get_logger().info(f'executing: {action}')
        feedback = Execute.Feedback()
        for i, phase in enumerate(PHASES):
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()
                self.get_logger().info(f'canceled before {phase}')
                return Execute.Result(success=False, message=f'canceled before {phase}')
            time.sleep(1.0)   # the "work"
            feedback.phase = phase
            feedback.progress = (i + 1) / len(PHASES)
            goal_handle.publish_feedback(feedback)
        goal_handle.succeed()
        self.get_logger().info(f'done: {action}')
        return Execute.Result(success=True, message=f'{action}: done')


def main():
    rclpy.init()
    executor = MultiThreadedExecutor()
    executor.add_node(Robot())
    executor.spin()


if __name__ == '__main__':
    main()
    • ActionServer(self, Execute, 'execute', execute_callback=..., cancel_callback=...) offers an action called execute. By default every goal is accepted.
    • execute(goal_handle) runs once per goal. The request is in goal_handle.request. It loops over the four phases: it "works" (time.sleep(1.0) stands in for moving the arm), then sends progress with goal_handle.publish_feedback(...).
    • At the start of every phase it asks goal_handle.is_cancel_requested. If true, it ends the goal with goal_handle.canceled() and returns a result. Otherwise, after the last phase, goal_handle.succeed() and a result with success=True. (goal_handle.abort() would end with status ABORTED.) Your code decides when to look at the cancel flag, so the arm can only stop at points where that is safe: here, between phases.
    • cancel_callback answers "may this goal be cancelled?". We always say ACCEPT.
    • MultiThreadedExecutor and ReentrantCallbackGroup: while execute is busy sleeping, ROS 2 must still be able to receive a cancel request. With the single-threaded executor of A1 and A2 it could not, because that one thread would be stuck inside execute. We tested it: without these two lines, a cancel request made during the goal is not answered until the goal has already finished, and then it finds nothing left to cancel (goals_canceling=[]), so the goal succeeds. These two lines allow several callbacks to run at the same time.

    This is code/03-actions/cpp/src/server.cpp:

    // Action server /execute: pretends to carry out a symbolic action in four phases (1 s each).
#include <memory>
#include <string>
#include <thread>
#include <vector>

#include "rclcpp/rclcpp.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
#include "a3_interfaces/action/execute.hpp"

using Execute = a3_interfaces::action::Execute;
using GoalHandle = rclcpp_action::ServerGoalHandle<Execute>;
using namespace std::chrono_literals;

const std::vector<std::string> PHASES = {"approach", "grasp", "lift", "place"};

class Robot : public rclcpp::Node
{
public:
  Robot() : Node("robot")
  {
    using namespace std::placeholders;
    server_ = rclcpp_action::create_server<Execute>(
      this, "execute",
      [](const rclcpp_action::GoalUUID &, std::shared_ptr<const Execute::Goal>) {
        return rclcpp_action::GoalResponse::ACCEPT_AND_EXECUTE;   // accept every goal
      },
      [](const std::shared_ptr<GoalHandle>) {
        return rclcpp_action::CancelResponse::ACCEPT;             // accept every cancel request
      },
      [this](const std::shared_ptr<GoalHandle> goal_handle) {
        // Run on a separate thread, so this callback returns at once and the node keeps
        // handling other requests (such as a cancel) while the action runs.
        std::thread([this, goal_handle]() { execute(goal_handle); }).detach();
      });
  }

private:
  void execute(const std::shared_ptr<GoalHandle> goal_handle)
  {
    std::string action = goal_handle->get_goal()->name;
    for (const auto & arg : goal_handle->get_goal()->args) {
      action += " " + arg;
    }
    RCLCPP_INFO(get_logger(), "executing: %s", action.c_str());

    auto feedback = std::make_shared<Execute::Feedback>();
    auto result = std::make_shared<Execute::Result>();
    for (size_t i = 0; i < PHASES.size(); ++i) {
      if (goal_handle->is_canceling()) {
        result->success = false;
        result->message = "canceled before " + PHASES[i];
        goal_handle->canceled(result);
        RCLCPP_INFO(get_logger(), "canceled before %s", PHASES[i].c_str());
        return;
      }
      std::this_thread::sleep_for(1s);   // the "work"
      feedback->phase = PHASES[i];
      feedback->progress = static_cast<float>(i + 1) / PHASES.size();
      goal_handle->publish_feedback(feedback);
    }
    result->success = true;
    result->message = action + ": done";
    goal_handle->succeed(result);
    RCLCPP_INFO(get_logger(), "done: %s", action.c_str());
  }

  rclcpp_action::Server<Execute>::SharedPtr server_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<Robot>());
  rclcpp::shutdown();
  return 0;
}
    • rclcpp_action::create_server<Execute>(this, "execute", ...) offers an action called execute, with three functions: one decides about a new goal (we ACCEPT_AND_EXECUTE every goal), one decides about a cancel request (we always ACCEPT), and one is called once a goal is accepted. The result is kept in the member server_ (as in A2: the server exists only while this handle is alive).
    • The third function starts execute on a new thread and returns immediately. Otherwise the node would be stuck inside execute for the whole action and could not receive a cancel request in the meantime. We tested it: without the thread, a cancel request made during the goal is not answered until the goal has already finished, and then it finds nothing left to cancel (goals_canceling=[]), so the goal succeeds.
    • execute(goal_handle) runs once per goal. The request is goal_handle->get_goal(). It loops over the four phases: it "works" (sleep_for(1s) stands in for moving the arm), then sends progress with publish_feedback.
    • At the start of every phase it asks goal_handle->is_canceling(). If true, it ends the goal with canceled(result). Otherwise, after the last phase, succeed(result). (abort(result) would end with status ABORTED.) Your code decides when to look at the cancel flag, so the arm can only stop at points where that is safe: here, between phases.
    • The package's CMakeLists.txt and package.xml add the library rclcpp_action next to rclcpp.

  7. Read and run a client

    This is code/03-actions/py/client.py:

    #!/usr/bin/env python3
"""Sends one goal to /execute and prints feedback and result, for example: python3 client.py unstack F W"""
import sys

import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from a3_interfaces.action import Execute


def main():
    rclpy.init()
    node = Node('robot_client')
    client = ActionClient(node, Execute, 'execute')
    client.wait_for_server()

    goal = Execute.Goal()
    goal.name = sys.argv[1]
    goal.args = sys.argv[2:]

    # 1. send the goal; the feedback callback runs for every feedback message
    send_future = client.send_goal_async(
        goal, feedback_callback=lambda msg: print(f'feedback: {msg.feedback.phase} ({msg.feedback.progress:.2f})'))
    rclpy.spin_until_future_complete(node, send_future)
    goal_handle = send_future.result()
    if not goal_handle.accepted:
        print('goal rejected')
        return

    # 2. wait for the result
    result_future = goal_handle.get_result_async()
    rclpy.spin_until_future_complete(node, result_future)
    result = result_future.result().result
    print(f'result: success={result.success} message={result.message}')
    rclpy.shutdown()


if __name__ == '__main__':
    main()
    • ActionClient(node, Execute, 'execute') is the handle for an action. wait_for_server() waits until a server exists.
    • send_goal_async(goal, feedback_callback=...) sends the goal and returns a future (as in A2). The feedback callback runs for every feedback message that arrives.
    • The answer to the send is a goal handle. goal_handle.accepted says whether the server accepted the goal.
    • goal_handle.get_result_async() returns a second future, for the final result, and we wait on that too. The goal handle is also what you would use to cancel: goal_handle.cancel_goal_async().

    This is code/03-actions/cpp/src/client.cpp:

    // Sends one goal to /execute and prints feedback and result, for example: ros2 run a3_actions client unstack F W
#include <cstdio>
#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
#include "a3_interfaces/action/execute.hpp"

using Execute = a3_interfaces::action::Execute;
using GoalHandle = rclcpp_action::ClientGoalHandle<Execute>;

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("robot_client");
  auto client = rclcpp_action::create_client<Execute>(node, "execute");
  if (!client->wait_for_action_server(std::chrono::seconds(10))) {
    RCLCPP_ERROR(node->get_logger(), "no action server /execute");
    return 1;
  }

  Execute::Goal goal;
  goal.name = argv[1];
  for (int i = 2; i < argc; ++i) {
    goal.args.push_back(argv[i]);
  }

  // The callbacks: the feedback callback runs for every feedback message,
  // the result callback once, when the goal ends.
  rclcpp_action::Client<Execute>::SendGoalOptions options;
  options.feedback_callback =
    [](GoalHandle::SharedPtr, const std::shared_ptr<const Execute::Feedback> feedback) {
      std::printf("feedback: %s (%.2f)\n", feedback->phase.c_str(), feedback->progress);
    };
  options.result_callback = [](const GoalHandle::WrappedResult & wrapped) {
    std::printf("result: success=%s message=%s\n", wrapped.result->success ? "True" : "False",
      wrapped.result->message.c_str());
  };

  // 1. send the goal
  auto goal_future = client->async_send_goal(goal, options);
  rclcpp::spin_until_future_complete(node, goal_future);
  auto goal_handle = goal_future.get();
  if (!goal_handle) {
    std::printf("goal rejected\n");
    return 1;
  }

  // 2. wait for the result (its callback prints it)
  auto result_future = client->async_get_result(goal_handle);
  rclcpp::spin_until_future_complete(node, result_future);
  rclcpp::shutdown();
  return 0;
}
    • rclcpp_action::create_client<Execute>(node, "execute") is the handle for an action. wait_for_action_server waits until a server exists.
    • SendGoalOptions collects the callbacks: feedback_callback runs for every feedback message that arrives, and result_callback runs once at the end. Both are small unnamed functions (lambdas). The options are given when the goal is sent, not later, because feedback can arrive before you have the goal handle. Step 2 only waits for the end.
    • async_send_goal sends the goal and returns a future (as in A2). The answer is a goal handle; an empty one means the goal was rejected.
    • async_get_result(goal_handle) returns a second future, for the final result, and we wait on that too. The goal handle is also what you would use to cancel: client->async_cancel_goal(goal_handle).

5. Exercise

With the server running, start the client for unstack F W in terminal 2. About 1.5 seconds later, start a second client in terminal 3 with pickup W. What does the server do with the second goal, and is that sensible for a robot arm?

Answer

Both goals run at the same time and both succeed. In the server's log the second executing line appears 1.5 seconds after the first, and the two done lines come 4 seconds after their own starts:

executing: unstack F W
executing: pickup W
done: unstack F W
done: pickup W

That is because our goal function accepts every goal and each goal gets its own thread of execution. For an arm this is wrong: one arm cannot do two things at once. A real server rejects a goal while it is busy (the goal function returns GoalResponse.REJECTrclcpp_action::GoalResponse::REJECT), or queues it, or cancels the current one first. The client sees a rejected goal as goal rejected, with the check we wrote after sending. Part D will do exactly this for the arm.

6. Recap

  • An action is for a long job: a goal goes in, feedback flows while it runs, one result comes out, and the client may cancel. The .action file has three parts separated by ---: goal, result, feedback.
  • A goal ends as SUCCEEDED, CANCELED or ABORTED.
  • Underneath, an action is three hidden services (send goal, cancel, get result) and two hidden topics (feedback, status).
  • The server must stay responsive during the job so a cancel request can arrive: a multi-threaded executor in Python, a worker thread in C++. It checks the cancel flag at safe points.
  • Inspect with ros2 action list -t, ros2 action info, send with ros2 action send_goal --feedback.
