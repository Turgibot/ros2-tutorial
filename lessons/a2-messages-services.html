A2 · Messages and services

Define your own message type, then build a service that answers questions about it.

Before we start: the scenario

The course ends with a robot arm that rearranges lettered blocks on a table. The blocks are cubes labelled with letters (F, W, ...) and can be stacked into towers. We do not tell the arm joint angles. We tell it symbolic actions: short commands about blocks, such as unstack F W. The arm turns each one into motion. Later lessons build that. This lesson only prepares the vocabulary, so you need to know the four actions:

ActionMeaningNeeds
pickup XTake block X from the table and hold it.1 block
putdown XPut the block you are holding, X, down on the table.1 block
stack X YPut the block you are holding, X, on top of block Y.2 blocks
unstack X YTake block X, which is on top of block Y, off the tower and hold it.2 blocks

The rules of this little world: the arm holds one block at a time, and it can only move a block that has nothing on top of it. So in the picture, F is on W, and unstack F W lifts F off and leaves W alone on the table. stack F W would do the reverse.

To send such a command between programs, ROS 2 needs a message that can hold it, and a way to ask "is this a valid action?". That is what this lesson builds.

1. Goal

At the end of this lesson you will have:

  • defined a message, SymbolicAction, that holds an action such as unstack F W, and a service, CheckAction, that says whether such an action is well formed,
  • built them into a package and inspected them with ros2 interface,
  • sent your message on a topic from the command line,
  • started a service server and called it from the command line and from a client program.

Here we only teach the tools, with a tiny checker; the arm itself comes later.

2. Concepts

Interfaces: message, service

In A1 we used a ready-made message, std_msgs/msg/String. Its definition is one line, string data. You can define your own the same way, in a small text file. Such definitions are called interfaces: the agreement between programs about what they exchange. Two programs can only talk if both build their data from the same definition, which is why it is called an interface (the meeting point between them), and why it lives in a file of its own. There are two kinds you need now:

  • a message (.msg file): a list of fields, each with a type and a name. It is sent on a topic.
  • a service (.srv file): a request and a response, separated by a line with three dashes (---). A service is an interface too, because a client and a server must agree on both parts: what the question contains and what the answer contains. The build turns the two halves into two message types, CheckAction_Request and CheckAction_Response (you will see these names in the output below).

Field types include bool, int32, float64, string, another message (like SymbolicAction inside our service), and lists of these, written with [] (string[] is a list of strings).

When you build a package that contains such files, ROS 2 generates Python and C++ code for them. That is why the same interface can be used from both languages, and from programs written by different people.

Topic or service?

A topic is a continuous one-way stream: the publisher sends whenever it likes and does not wait for anyone. A service is a question and an answer: a client sends one request, the server computes and sends one response, and the client waits for it. Use a topic for data that keeps flowing (joint positions). Use a service for a short question that needs an answer (is this action valid?). Something that takes a long time and needs progress updates is neither: that is an action, lesson A3.

3. Do it

All commands run in a container shell (A0, step 5). You will use two terminals, called 1 and 2. The code is in code/02-messages-services/. Use the Python / C++ switch at the top right to choose your language. The interfaces are the same for both.

  1. Read the interfaces

    The interfaces live in their own package, code/02-messages-services/interfaces/. Here is the message, msg/SymbolicAction.msg:

    # One symbolic action, for example: unstack F W
string name        # the action: pickup, putdown, stack or unstack
string[] args      # the blocks it applies to, for example [F, W]

    Two fields: the action's name (unstack) and a list of strings, args ([F, W]). Everything after # is a comment. The file name, SymbolicAction, becomes the type name, so it must start with a capital letter. And this is the service, srv/CheckAction.srv:

    # Request: an action to check
SymbolicAction action
---
# Response: is it well formed, and why not
bool valid
string reason

    The request is one SymbolicAction (our message, used as a field type). The response has two fields: valid (yes or no) and reason (a sentence).

    The package also needs two small files that say what to generate. You do not need to change them now, lesson A4 explains packages. CMakeLists.txt lists the interface files:

    rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/SymbolicAction.msg"
  "srv/CheckAction.srv"
  DEPENDENCIES   # srv/CheckAction.srv uses the message above, which lives in this same package
)

    and package.xml gives the package its name, a2_interfaces.

  5. Read the server

    This is code/02-messages-services/py/server.py:

    #!/usr/bin/env python3
"""Service /check_action: says whether a symbolic action is well formed."""
import rclpy
from rclpy.node import Node
from a2_interfaces.srv import CheckAction

ARGUMENTS = {'pickup': 1, 'putdown': 1, 'stack': 2, 'unstack': 2}   # action -> how many blocks it needs


class Checker(Node):
    def __init__(self):
        super().__init__('checker')
        self.create_service(CheckAction, 'check_action', self.on_request)

    def on_request(self, request, response):
        name, args = request.action.name, request.action.args
        if name not in ARGUMENTS:
            response.valid, response.reason = False, f"unknown action '{name}'"
        elif len(args) != ARGUMENTS[name]:
            response.valid, response.reason = False, f'{name} needs {ARGUMENTS[name]} blocks, got {len(args)}'
        else:
            response.valid, response.reason = True, 'ok'
        self.get_logger().info(f'checked {name} {list(args)}: {response.reason}')
        return response


def main():
    rclpy.init()
    rclpy.spin(Checker())


if __name__ == '__main__':
    main()
    • from a2_interfaces.srv import CheckAction: the generated code, imported like any Python module. The package, the kind (srv) and the name match what ros2 interface list showed.
    • ARGUMENTS is a dictionary: for each known action, how many blocks it needs.
    • create_service(CheckAction, 'check_action', self.on_request): offer a service called check_action and call on_request for every request.
    • on_request(self, request, response) receives the request, fills in response.valid and response.reason, and returns the response. The reply goes to the caller when the function returns.

    This is code/02-messages-services/cpp/src/server.cpp:

    // Service /check_action: says whether a symbolic action is well formed.
#include <map>
#include <memory>
#include <string>

#include "rclcpp/rclcpp.hpp"
#include "a2_interfaces/srv/check_action.hpp"

using CheckAction = a2_interfaces::srv::CheckAction;

// action -> how many blocks it needs
const std::map<std::string, size_t> ARGUMENTS = {{"pickup", 1}, {"putdown", 1}, {"stack", 2}, {"unstack", 2}};

class Checker : public rclcpp::Node
{
public:
  Checker() : Node("checker")
  {
    service_ = create_service<CheckAction>(
      "check_action",
      [this](const std::shared_ptr<CheckAction::Request> request, std::shared_ptr<CheckAction::Response> response) {
        on_request(request, response);
      });
  }

private:
  void on_request(const std::shared_ptr<CheckAction::Request> request, std::shared_ptr<CheckAction::Response> response)
  {
    const std::string & name = request->action.name;
    const size_t count = request->action.args.size();
    auto rule = ARGUMENTS.find(name);
    if (rule == ARGUMENTS.end()) {
      response->valid = false;
      response->reason = "unknown action '" + name + "'";
    } else if (count != rule->second) {
      response->valid = false;
      response->reason = name + " needs " + std::to_string(rule->second) + " blocks, got " + std::to_string(count);
    } else {
      response->valid = true;
      response->reason = "ok";
    }
    RCLCPP_INFO(get_logger(), "checked %s (%zu blocks): %s", name.c_str(), count, response->reason.c_str());
  }

  rclcpp::Service<CheckAction>::SharedPtr service_;
};

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<Checker>());
  rclcpp::shutdown();
  return 0;
}
    • #include "a2_interfaces/srv/check_action.hpp": the generated header. The file name is the service name in lower case with underscores (CheckAction becomes check_action).
    • ARGUMENTS is a map: for each known action, how many blocks it needs.
    • create_service<CheckAction>("check_action", ...): offer a service called check_action and call the lambda for every request.
    • The result of create_service is stored in the member service_. This is required, not decoration: in C++ the service exists only while that handle is alive. We tested it: with the service_ = part removed, the server starts but /check_action does not even appear in ros2 service list, and a client waits forever. (Python keeps the handle inside the node for you, so server.py does not store it.)
    • on_request receives pointers to the request and to the response, fills in response->valid and response->reason, and the reply goes to the caller when the function ends.
    • The package's CMakeLists.txt says find_package(a2_interfaces REQUIRED), and package.xml has <depend>a2_interfaces</depend>: that is how the C++ build finds the generated code.

    Notice that the server code looks at the request and answers. It does not know who asked.

  7. Read and run a client

    Calling from the command line is handy for testing. A program calls services with a client.

    This is code/02-messages-services/py/client.py:

    #!/usr/bin/env python3
"""Asks /check_action about one action, for example: python3 client.py unstack F W"""
import sys
import rclpy
from rclpy.node import Node
from a2_interfaces.srv import CheckAction


def main():
    rclpy.init()
    node = Node('checker_client')
    client = node.create_client(CheckAction, 'check_action')
    while not client.wait_for_service(timeout_sec=1.0):
        node.get_logger().info('waiting for the service...')

    request = CheckAction.Request()
    request.action.name = sys.argv[1]
    request.action.args = sys.argv[2:]

    future = client.call_async(request)
    rclpy.spin_until_future_complete(node, future)
    response = future.result()
    print(f'valid={response.valid} reason={response.reason}')
    rclpy.shutdown()


if __name__ == '__main__':
    main()
    • create_client(CheckAction, 'check_action'): a handle for calling that service. wait_for_service blocks until a server exists, so the client does not send a request into the void.
    • CheckAction.Request() creates an empty request. We fill in the nested message with the words typed on the command line: sys.argv[1] is the first word after the program name, sys.argv[2:] are the rest.
    • call_async(request) sends it and returns a future, a placeholder for the answer that has not arrived yet. spin_until_future_complete runs ROS 2 until the answer arrives, and future.result() is the response.

    This is code/02-messages-services/cpp/src/client.cpp:

    // Asks /check_action about one action, for example: ros2 run a2_services client unstack F W
#include <chrono>
#include <iostream>
#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "a2_interfaces/srv/check_action.hpp"

using CheckAction = a2_interfaces::srv::CheckAction;
using namespace std::chrono_literals;

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = rclcpp::Node::make_shared("checker_client");
  auto client = node->create_client<CheckAction>("check_action");
  while (!client->wait_for_service(1s)) {
    if (!rclcpp::ok()) {   // Ctrl+C while waiting: stop instead of looping forever
      return 1;
    }
    RCLCPP_INFO(node->get_logger(), "waiting for the service...");
  }

  auto request = std::make_shared<CheckAction::Request>();
  request->action.name = argv[1];
  for (int i = 2; i < argc; ++i) {
    request->action.args.push_back(argv[i]);
  }

  auto future = client->async_send_request(request);
  rclcpp::spin_until_future_complete(node, future);
  auto response = future.get();
  std::cout << "valid=" << (response->valid ? "True" : "False") << " reason=" << response->reason << std::endl;
  rclcpp::shutdown();
  return 0;
}
    • create_client<CheckAction>("check_action"): a handle for calling that service. wait_for_service blocks until a server exists, so the client does not send a request into the void.
    • std::make_shared<CheckAction::Request>() creates an empty request. We fill in the nested message with the words typed on the command line: argv[1] is the first word after the program name, argv[2] onwards are the rest.
    • async_send_request(request) sends it and returns a future, a placeholder for the answer that has not arrived yet. spin_until_future_complete runs ROS 2 until the answer arrives, and future.get() is the response.

    container With the server still running in terminal 1, run the client in terminal 2 three times, with a good action, a wrong count, and an unknown action:

5. Exercise

Predict the response to pickup with no blocks, then check it with the client (python3 py/client.py pickupros2 run a2_services client pickup). Then answer: why is "is this action valid?" a service and not a topic?

Answer

pickup needs 1 block and we give 0, so the server reports it the same way as for stack:

valid=False reason=pickup needs 1 blocks, got 0

It is a service because the caller needs an answer to one specific question before it goes on, and wants it matched to that request. A topic would stream answers to anyone listening, with no link between a question and its answer, and the sender would not know whether anyone received it.

6. Recap

  • An interface is a text file defining data: a .msg (fields, sent on a topic) or a .srv (request --- response).
  • Building the interface package generates Python and C++ code. Use it as package.srv / package.msg imports in Python and package/srv/name.hpp includes in C++. Source install/setup.bash in every new shell.
  • A service is a request and a response. The server offers it with create_service; the client calls it with create_client and waits for the answer.
  • Inspect with ros2 interface list/show, ros2 service list -t, and call by hand with ros2 service call.
  • Topic for a stream, service for a question. Long jobs with progress are actions (A3).
